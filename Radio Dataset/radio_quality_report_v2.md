## 13. Limitations and unresolved questions

1. The raw per-scenario CSV/JSON radio files and the dataset documentation are not in the repository, so duplicate causes, PHR/RSSI/RSRP semantics, counter semantics and logger/packet-capture clock synchronisation could not be verified at source.
2. The RNTI-change/reset relationship is verified for THIS dataset only; it is asserted, not assumed to be a general rule.
3. A byte delta covers `(previous timestamp_ms, timestamp_ms]`, whose position inside one-second network windows depends on the millisecond phase of each UE's sampling. Which network window a delta belongs to is therefore an alignment decision still to be made (the interval bounds are kept for it); the end-second bucket used here is a convention only.
4. Statistics over simultaneous UEs pool them: no UE-to-flow mapping exists, so this is temporal aggregation, not per-flow measurement. Std is 0 by construction when a second has one report; use `<kpi>_n` and `n_ue_reporting` to see this.
5. Primary statistics keep all-zero UL reports (raw values); the `_nz` variants are the sensitivity alternative. Which is appropriate depends on what such records mean, which is undocumented.
6. KPIs with eta-squared >= 0.5 (section 4): rsrp, rssi, sinr, dlMcs, ri, phr; 1 of them in the conservative core. Capture/session dependence cannot be removed by this preprocessing. Any later separation between scenario groups must not be read as attack evidence without controlling for it.
7. Windows with no valid PUSCH report have NaN `puschSnr_*`; downstream code must handle missing values explicitly.
